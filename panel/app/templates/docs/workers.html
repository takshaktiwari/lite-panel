What workers are for

Some jobs must run all the time, not on a schedule: a Laravel queue worker that sends emails and processes uploads, Horizon, Reverb (WebSockets), a Celery worker, a Node job runner. A worker is a command the panel keeps running in the background: it restarts if it crashes, starts again after a reboot, and runs as the site's own unprivileged user, so it can only touch that site's files.

Workers are available on every site type. Find them in the Workers section of a site's page.

How it works

The panel uses systemd, the service manager already on the server, which also runs your Node.js and Python apps. There is nothing extra to install and no separate process manager such as Supervisor to maintain. Each worker becomes a unit named lite-panel-worker-<site>.<name>@N.service (one per process). Output goes to the system journal, so it is rotated automatically.

The units are generated from the panel's database, so lite-panel rebuild recreates them. Don't edit the unit files by hand: changes are overwritten.

Adding a worker

  1. Open the site, scroll to Workers and open Add a worker.
  2. Pick a preset (this fills in the name and command), or type your own.
  3. Set the number of processes and the stop timeout, then click Add and start.
FieldMeaning
NameLowercase letters, digits and hyphens (up to 24). Unique within the site.
CommandThe command to run. {PHP} is replaced by the site's PHP binary (for example /usr/bin/php8.3), so the worker follows the site's PHP version.
ProcessesHow many copies run in parallel (1 to 8). Use more than one to work through a queue faster.
Stop timeoutSeconds the worker is given to finish its current job after a stop or restart before it is killed. Set it longer than your slowest job.

The command runs from the project folder. For a PHP site whose document path ends in public (Laravel), that is the folder above public, where artisan lives. For Node.js and Python sites it is the app folder.

Laravel

PresetCommand
Queue worker{PHP} artisan queue:work --sleep=3 --tries=3 --max-time=3600
Horizon{PHP} artisan horizon
Reverb{PHP} artisan reverb:start
Scheduler{PHP} artisan schedule:work
  • Set QUEUE_CONNECTION in the project's .env to a real driver (database or redis); with sync there is nothing for a worker to do.
  • --max-time=3600 makes the worker exit cleanly every hour so memory leaks cannot build up; systemd starts it again immediately.
  • The scheduler preset is an alternative to the cron entry for schedule:run. Use one or the other, not both.
After every deployWorkers keep the old code in memory until they restart. After deploying, click Restart all on the site's Workers section. A restart is graceful: the current job finishes (up to the stop timeout) before the worker exits.

Node.js and Python

Workers on application sites use the same environment as the app: the environment variables from the app settings, node_modules/.bin (Node.js) or the virtualenv (Python) on PATH. Examples: node worker.js, celery -A app worker -l info, rq worker. Install dependencies first (see Node.js & Python apps).

Managing workers

  • Start / Restart / Stop per worker. Stop also keeps it from starting at boot until you start it again.
  • Restart all restarts every worker of the site.
  • Logs shows the most recent output of all of a worker's processes. Also available in the Logs page's journal view for the unit.
  • Edit or remove changes the command, process count or stop timeout (a running worker is restarted to apply it), or deletes the worker and its units.
  • Changing the site's PHP version restarts its running {PHP} workers on the new version. Deleting the site removes all its workers.

If a worker won't stay running

The job log shows the worker's last output when it exits right after starting. The usual causes:

  • Dependencies missing: run composer install (PHP) or Install dependencies (Node.js / Python) first.
  • Wrong folder or file: artisan must be in the project folder described above. Check the document path on the site page.
  • The command uses {PHP} but the site has no PHP version: choose one under PHP version on the site page.
  • Permissions: the worker runs as the site user, so storage/ and bootstrap/cache must be writable by it.
